# Headphone measurement & correction data landscape

Research base: [AutoEq](https://github.com/jaakkopasanen/AutoEq) ([`results/`](https://github.com/jaakkopasanen/AutoEq/tree/master/results), [`targets/`](https://github.com/jaakkopasanen/AutoEq/tree/master/targets), [INDEX.md](https://raw.githubusercontent.com/jaakkopasanen/AutoEq/master/results/INDEX.md)), [autoeq.app](https://autoeq.app), [OPRA](https://github.com/opra-project/OPRA) ([opra.roon.app](https://opra.roon.app)), [squig.link](https://github.com/squiglink) ([CrinGraph](https://github.com/mlochbaum/CrinGraph), [Squig-Rank](https://github.com/PEQHUB/Squig-Rank)), [peqdb.com](https://peqdb.com) (via [OnlyEQ](https://github.com/zollans/OnlyEQ)'s `OnlineDatabase.swift`), [Room EQ Wizard](https://www.roomeqwizard.com/), [GitHub's May 2025 unauth rate-limit change](https://github.blog/changelog/2025-05-08-updated-rate-limits-for-unauthenticated-requests/). Current `eq` state, for reference: `Sources/eq/Import/AutoEqIndex.swift` (index parse/match/fetch, `preferredSources = ["oratory1990", "crinacle", "Rtings"]`), `README.md`'s "AutoEq" section (`eq import`, `--source`, `--keep-bands`), 7-day cache at `~/.cache/eq/autoeq`.

## AutoEq itself: still the right backbone, but read the README's own disclaimer

`jaakkopasanen/AutoEq` is MIT-licensed and actively maintained — commits as recent as 2025-07-20 adding new measurement sources (Rtings v1.8, "Squigsites" crawling, HypetheSonics, Regan Cipher). `results/` today has 27 source directories, not just the three `eq` prefers: oratory1990, crinacle, Rtings, Innerfidelity, Headphone.com Legacy, Super Review, Ted's Squig Hoard, and more. `INDEX.md` (8854 lines) keeps the exact format `AutoEqIndex.parse` already expects: `- [Name](./source/rig/Name) by Source on Rig`, ANC/mode variants inline as parenthetical suffixes.

The repo's own README now says plainly: *"This Github repository now mainly serves developers"* and that the precomputed files in `results/` *"should not be used by normal users since **autoeq.app** exists."* That's not a knock on `eq` — a CLI fetching `INDEX.md` and a `ParametricEQ.txt` programmatically is exactly the "developer" use case the README is fine with; it's aimed at people manually browsing GitHub folders. No change forced here, but it means `eq` should not expect autoeq.app's web UI to keep pointing back at `results/` forever, and should treat `results/`+`INDEX.md` as a stable *data* interface rather than a user-facing one.

**autoeq.app** is a client-heavy SPA; I could not confirm a stable public JSON API for it. A community fork ([`M0Rf30/AutoEq`](https://github.com/M0Rf30/AutoEq)) documents a `POST /process` endpoint (`calibration`, `compensation` target, `max_filters`, `bass_boost`) that looks like the real backend — unverified as canonical or stable. **Do not build on it now**; it would let `eq` request a *freshly computed* correction against an arbitrary target/bass-boost instead of only the one precomputed variant GitHub ships, which is attractive, but not on unverified, undocumented infrastructure.

**Targets** live in `targets/` as CSVs: Harman over-ear 2013/2015/2018 (± "without bass"), Harman in-ear 2016/2017-1/2017-2/2019 (± "without bass"), diffuse-field (ISO 11904-1), free-field (ISO 11904-2), Harman loudspeaker in-room-flat 2013, plus per-source self-targets. Each `results/` entry is precomputed against **one** target chosen by whoever ran the AutoEq pipeline for that source/model (almost always a Harman curve) — `eq import` has no way to ask for the diffuse-field variant of a model that only has a Harman-target result, because it doesn't exist as a separate file. That's a real, permanent limitation of consuming precomputed results rather than running the regression yourself.

**Regeneration**: AutoEq's Python pipeline ingests raw FR measurements per source and recomputes parametric/graphic EQ against chosen targets; cadence is "whenever a maintainer or a source pushes new measurements," not a fixed schedule — evidenced by irregular commit spacing.

**Licensing**: whole repo is MIT. Caching and redistributing files out of `results/` (which is what `eq`'s cache directory already does) is legally clean — MIT requires only that the license/copyright notice travel with copies of the *code*; the data files carry no separate license text asserting otherwise. Underlying-source attribution (oratory1990/crinacle/Rtings by name) is a community norm, not a license clause — `eq` already surfaces it via the `source` field and should keep doing so in every `import` confirmation.

**Rate limits**: `raw.githubusercontent.com` unauthenticated limits tightened in [May 2025](https://github.blog/changelog/2025-05-08-updated-rate-limits-for-unauthenticated-requests/) — no fixed published number, per-IP throttling, users report 429s under the old informal ~60/hr figure. `eq`'s 7-day cache (`AutoEqCache.load`) plus stale-cache fallback on fetch failure (`AutoEqIndex.swift:104-108`) is already the correct mitigation shape; the one gap worth checking is whether the fetch client sends any `User-Agent` — GitHub's raw CDN is known to be stricter with none.

Net: **AutoEq stays primary, OPRA is the one credible secondary source worth adding** (clear license, structured, multi-target). Everything squig.link/crinacle-flavored should stay strictly reference/link-out, never cached or redistributed.

## User workflows

**Target choice.** AutoEq's own CLI defaults to Harman over-ear 2018 for over-ears and Harman in-ear 2019 for IEMs (`--target=targets/<file>.csv`), and Harman is not "flat" — it's a preference-study curve with ~4-6 dB of sub-bass boost and an ear-canal-resonance bump near 3 kHz. Listeners who find that too warm/dark reach for diffuse-field, free-field, or crinacle's "IEF Neutral" (available via OPRA, not AutoEq). Because `results/` ships one precomputed target per entry, `eq import` inherits whatever target the original AutoEq run used — it cannot currently offer "same headphone, diffuse-field instead."

**Preference layers on top of the correction**, confirmed from AutoEq's own docs: `--bass-boost=<gain>` or `<gain,Fc,Q>` (low shelf, default Fc 105 Hz, Q 0.7, default gain 6 dB), `--treble-boost=<gain>` or `<gain,Fc,Q>` (high shelf, default Fc 10 kHz, Q 0.7), `--tilt=<dB/octave>` (broadband slope, positive = brighter). These are deliberately separate from target-matching — the correction is fixed, precomputed data; the shelf/tilt is a small number of parameters a person tunes live. That maps directly onto `eq`'s own split between an imported correction and the ten hand-tuned bands (`--keep-bands`): the natural next step is treating bass-boost/treble-boost/tilt as a *third* layer — adjustable shelves stacked on top of an imported correction, distinct from both the correction itself and the hand-tuned graphic bands.

**Room/speaker EQ (REW) is a different problem, not a bridge.** [Room EQ Wizard](https://www.roomeqwizard.com/) measures a specific room with a calibrated mic (e.g. UMIK-1) at one listening position, correcting standing waves and reflections that are unique to that room and chair. Headphone correction has no analogous "room" — the published measurement is from a fixed HATS coupler, corpus-driven rather than measurement-driven. Worth keeping as a one-line contrast in `eq`'s docs (why speakers aren't "just another `eq import` target"), not as a feature to build toward.

**ANC/BT device-state variants are real and already named in AutoEq.** Entries carry parenthetical suffixes — `(ANC on)`, `(ANC off)`, `(passive)`, `(transparency mode)` — standardized as of AutoEq 4.0.0. A model like AirPods Pro 2 ships as three or more separate entries. Nothing in the OS or the device tells `eq` which state is active, so this must stay a user choice, but it currently surfaces as a raw `.ambiguous([String])` list (`AutoEqIndex.match`, `Match.ambiguous`) — the full disambiguation burden lands on the user typing the exact bracketed variant.

## Recommendations for `eq`

1. **Keep AutoEq `results/`+`INDEX.md` as the default and only always-on source.** It's stable, MIT-licensed, actively maintained, and the README's "for developers" language is a green light for programmatic use, not a deprecation notice.
2. **Add OPRA as an optional second source** (`--source opra`, or fold into the existing `preferredSources` ranking as a fourth entry after Rtings) — it's the only alternative here with an explicit, permissive license (CC BY-SA 4.0) and machine-readable JSON. Treat peqdb.com as experimental-only if added at all (`--source peqdb --experimental` or similar), given the total absence of stated terms; never make it a silent fallback.
3. **Never scrape or cache squig.link/crinacle/Rtings/headphones.com/ASR data directly.** Their measurement data is either explicitly non-public or has no reuse terms at all; AutoEq's own `results/Rtings` and `results/crinacle` folders are the only sanctioned path to that data, since AutoEq presumably has its own arrangement or fair-use basis for redistributing it. `eq` inherits that arrangement only through AutoEq, not by going to the source sites itself.
4. **Improve matching for real-world queries, not just substring `.contains`.** `AutoEqIndex.match` (lines 37-65) does case-insensitive substring matching, exact-match narrowing, then `.ambiguous` on multiple distinct names. Two concrete gaps worth closing: (a) treat bracketed variant tags (`ANC on/off`, `transparency mode`, `wired`/`passive`) as a separate filterable token — e.g. `eq import "AirPods Pro" --variant "anc off"` — instead of forcing the user to retype the full bracketed name from an `.ambiguous` list; (b) add lightweight fuzzy matching (edit distance on the non-variant part of the name) for typos and model-number formatting differences (`WH1000XM4` vs `WH-1000XM4`), since AutoEq/Rtings/crinacle each format model numbers slightly differently across the same physical headphone.
5. **Add bass-boost / treble-boost / tilt as a distinct adjustable layer**, mirroring AutoEq's own shelf math exactly (low shelf ~105 Hz Q 0.7, high shelf ~10 kHz Q 0.7, broadband tilt in dB/octave) so a user's mental model transfers directly from AutoEq's docs. Implement as a small set of biquads applied after the imported correction and independent of `--keep-bands`'s hand-tuned bands — three layers total: measured correction (fixed), preference shelf/tilt (a few numbers), hand-tuned bands (fully free). Formulas are public (AutoEq's own README), no need to depend on the unverified autoeq.app `/process` endpoint.
6. **Keep the current offline/stale-cache behavior — it already matches best practice.** `AutoEqCache.load`'s stale-on-failure fallback (lines 104-109) and the empty-index-counts-as-failure guard (lines 98-100, guarding against captive-portal HTML masquerading as a 200) are both exactly right; no change needed beyond possibly adding a `User-Agent` header if 429s are ever observed in practice.
7. **Keep showing the `source` field in every import confirmation** (already does, via `AutoEqEntry.source`) — that's the entire attribution mechanism this ecosystem runs on, and it costs nothing to preserve.
8. **Treat "one target per precomputed entry" as a documented, permanent limitation**, not a bug — note it in `README.md`'s AutoEq section so users understand why `eq import "HD 600" --target diffuse-field` isn't a real flag today (it would require running AutoEq's regression pipeline live, which is out of scope for a lightweight importer, or waiting on OPRA to cover more targets/models over time).
