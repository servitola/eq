# Equalizer landscape — what people actually use, and what `eq` is missing

Research base: parallel primary-source surveys across macOS (GUI + the 2026-vintage Core-Audio-process-tap OSS cluster), Windows, Linux/headless DSP, and mobile/hardware. Sourcing prioritizes project docs, GitHub READMEs/issues, and firsthand forum/Reddit/HN/Play-Store accounts over marketing copy and aggregator summaries; aggregator-only claims are flagged inline as such. `eq`'s own state for reference: `README.md`, `CHANGELOG.md` (2026.09.27.4) — 10 graphic bands + up to 32 imported parametric filters, per-device curves, AutoEq import by name, `--json` everywhere, `eq doctor`, `eq watch`/`eq stream`, presets+undo "in progress."

## Method note on `eq`'s real competitive set

The obvious comparison (eqMac, SoundSource, Boom 3D) is the wrong frame. Apple's Core Audio process-tap API (macOS 14.2/14.4, 2024) removed the need for a virtual driver or kernel extension, and a cottage industry of small, mostly solo-developer macOS system EQs has appeared since — **OnlyEQ, iQualize, GlassEQ, core-eq, SystemEQ-for-Mac, MacEQ, SoundMax, cvknage/equaliser** — nearly all created in a six-month window (Mar–Sep 2026), nearly all citing eqMac's driver-based unreliability by name as their reason for existing (iQualize's own README: *"the install process was a hassle... half the features were behind a 'Pro' paywall, and then their Mac crashed"*). `eq` already vendors one of these (OnlyEQ's engine, per `README.md`'s "How it works"). This cluster, not the legacy commercial apps, is where `eq` will actually be judged.

## What `eq` lacks, ranked

### (a) Table stakes — ship these, the evidence is not close

1. **Presets with real save/load/rename, and undo.** Already "in progress" per project context — this survey confirms it's universal: SoundSource, Boom 3D, OnlyEQ, iQualize, GlassEQ, core-eq, Peace, Voicemeeter, EasyEffects, Wavelet all have it. iQualize's full undo/redo is explicitly called out by its own issue tracker as core UX (e.g. [#205](https://github.com/DariusCorvus/iqualize/issues/205), a bug where a filter *state leak* on preset switch left audio wrongly high-passed — the exact class of bug a good undo/rollback story prevents). `eq`'s save-on-every-keystroke `watch` model raises the stakes for this: a fat-fingered `!` on band 1 is currently only reversible by counting steps back.
2. **Hand-editable parametric filters (freq/gain/Q/type), not just imported ones.** `README.md`'s own "Limits" section names this gap. Every serious parametric competitor surveyed — iQualize, GlassEQ, core-eq, CamillaDSP, Equalizer APO/Peace, EasyEffects' LSP EQ — lets a user author a filter from scratch, not only receive one from an import. Right now `eq import --clear` is the only way to remove a parametric filter, and there's no way to add one by hand at all; a user who wants "one custom notch at 3.2 kHz" for a room resonance or a sibilant recording has no path.
3. **A one-command daemon bootstrap.** README currently requires the user to run `launchctl bootstrap gui/$UID ~/Library/LaunchAgents/com.servitola.eq.plist` by hand after `eq init` — every GUI competitor auto-launches at login with no manual step. `eq init --start` (or folding the bootstrap into `eq init`) removes a friction point that has no competitive justification for staying manual.
4. **Bounded recovery from bad state, matching core-eq's own hard-won fixes.** core-eq shipped two proactive fixes worth matching exactly because they're generic Core-Audio footguns, not core-eq-specific: aggregate/multi-output devices silently returning zero-stream output with no OS-level error ([README](https://github.com/andreypudov/core-eq)), and audio-permission refusal silently muting the whole Mac rather than surfacing an error. `eq doctor` should explicitly probe both — a multi-output device as the current default, and a revoked-but-previously-granted permission — since Core Audio itself won't tell either tool it happened.

### (b) Differentiators worth building — no direct evidence of demand yet, but the gap is real and cheap relative to `eq`'s existing shape

1. **Per-app exclusion list**, not per-app EQ. iQualize auto-excludes apps actively using the microphone (FaceTime/WhatsApp/Discord/Zoom) specifically so calls aren't ducked by EQ processing; OnlyEQ ships a general per-app exclusion list. `eq` processes the whole system mix, so a call app currently gets the same curve as music — usually fine, occasionally wrong (a bass-boosted curve tuned for a podcast makes a Zoom caller sound boomy). A `--exclude` list keyed by bundle ID is a small, headless-compatible feature that doesn't reopen the per-app-EQ can of worms.
2. **A community/aggregator layer over AutoEq**, matching what `docs/research/03-headphone-data.md` already recommends (OPRA as a second source) but extending it to the multi-format import breadth OnlyEQ and GlassEQ have (EqualizerAPO, REW, WAV impulse responses) rather than staying AutoEq-only. `eq`'s AutoEq database is currently narrower in *format* terms than the newest OSS competitors, even though its *matching logic* (per `03-headphone-data.md`) is already more careful than most.
3. **Convolution/FIR support for headphone correction precision**, as GlassEQ, CamillaDSP, and EasyEffects' LSP convolver all offer, and as AutoEq itself recommends for corrections a 10-band graphic EQ can't fit exactly (`GraphicEQ.txt`-vs-`ParametricEQ.txt` accuracy tradeoff is already called out in `eq`'s own README). This is real DSP work, not a small patch — worth a dedicated spike before committing, but it directly targets `eq`'s own documented "close but not exact" caveat on `GraphicEQ.txt` reduction.
4. **Independent per-channel (L/R) trim.** A live, unaddressed OnlyEQ feature request ([#33](https://github.com/zollans/OnlyEQ/issues/33)) and a feature cvknage/equaliser ships — useful for asymmetric hearing loss or an unbalanced headphone unit. Low effort (one more gain stage per channel) relative to the rest of the filter graph `eq` already has.
5. **A widely-legible "why is this not working" permission story.** core-eq revised its permission-request dialog wording specifically because "System Audio Recording" sounds broader than what an EQ needs — worth an explicit pass on `eq`'s own prompt/doctor copy, since every process-tap tool in this survey (eqMac's driver-reinstall nags, iQualize's ad-hoc-signing friction, GlassEQ's unsigned quarantine clearing) shows first-run trust friction is the norm in this category, not the exception, and it's cheap to get ahead of.

### (c) Deliberately do NOT build — evidence says these don't fit a headless tool, or actively cause the competitors' worst bugs

1. **Per-app EQ.** This is the single most-requested GUI feature (SoundSource, Boom 3D's per-app mixer, Voicemeeter's whole architecture, Wavelet's core pitch) — and also architecturally incompatible with `eq`'s one-tap-on-the-system-mix design without either N per-app taps (real CPU/complexity cost) or a Voicemeeter-style virtual-routing model (real setup-complexity cost, and Voicemeeter's own users report it as the source of persistent crackling — [forums.tomsguide.com](https://forums.tomsguide.com/threads/voicemeeter-lagging-out.422777/), [Steam Community/Helldivers 2 thread](https://steamcommunity.com/)). `README.md`'s "Limits" already excludes this correctly; this survey found nothing to overturn that call.
2. **A GUI, menu-bar icon, AU/VST plugin hosting, or spectrum-analyzer window.** `eq`'s entire value proposition against eqMac ("no icon, no window") is validated directly by iQualize's own founding complaint about eqMac's *"tiny and fiddly"* UI, and by the fact that every OSS competitor surveyed still ships as a menu-bar app — `eq` is alone in not doing this. AU hosting (SoundSource, Audio Hijack) is real power but pulls in a plugin-compatibility support burden with no headless equivalent; skip it.
3. **A virtual-driver or BlackHole fallback path for pre-14.4 macOS.** SystemEQ-for-Mac's dual-path strategy (native tap ≥14.4, BlackHole driver <13.x) and SoundMax's continued BlackHole dependency are exactly the older architecture generation whose failure modes (driver-reinstall nags, Gatekeeper blocks, routing conflicts — all self-documented in [SoundMax's own README](https://github.com/snap-sites/SoundMax)) `eq`'s process-tap-only design was built to avoid. `eq`'s README already states macOS 14.4+ as a hard floor; keep it hard rather than widening the install base at the cost of reintroducing the driver-class bugs this whole 2026 OSS generation exists to escape.
4. **Cloud sync / cross-machine preset sharing / a remote HTTP control server.** SoundSource's sync groups and eqMac Pro's HTTP API are the only precedents, and neither has documented demand evidence in this survey beyond "nice to have" — for a single-Mac, config-file-is-the-API tool, this adds a real attack surface (an open port) and sync-conflict class of bug for a feature nobody in the primary-source record specifically asked for. `~/.config/eq/eq.json` plus `--json` output is already the automation surface; anyone wanting remote control can already script over SSH.
5. **Chasing the largest possible bundled AutoEq database number as a marketing metric.** SystemEQ-for-Mac (8,665 models) and MacEQ (5,000+) lead on raw count, but `eq`'s `03-headphone-data.md` research already concluded AutoEq's own `results/`+`INDEX.md` plus an OPRA second source is the right, maintainable backbone — a bigger bundled SQLite blob is a vanity number, not evidence of better matches, and raises the exact staleness problem `eq`'s 7-day cache + `--refresh` already solves more honestly.
